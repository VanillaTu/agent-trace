## Context

见 proposal.md - Why(seed 盲区:invalid param retry,样本 <session-id>)。约束:只做审计产出文档,不触碰代码;真实会话样本在 `~/.dsh/sessions/--D-workspace--/`。

## Goals / Non-Goals

**Goals:**
- 系统性遍历真实会话,找出"发生了但 5 detector 没检出"的异常模式,产出盲区清单。
- 每个盲区带真实样本 + 事件类型 + 对应最初设计类别 + 建议 detector ID。

**Non-Goals:**
- 不实现任何新 detector(盲区清单是 backlog,立项走新 change)。
- 不做全量会话统计(只审计有代表性的样本,含错误/重试/长会话)。
- 不改代码、不改行为。

## Decisions

1. **人工核对 + 半自动辅助**:对每个样本会话,先跑 analyze 得到检出结果;再解压 JSONL 人工扫异常事件(工具报错/失败重试/大结果/空转等),两者对照找盲区。理由:盲区定义本身需要人工判断"这是不是异常",无法纯自动;半自动(analyze 先行)保证效率。
2. **盲区判定标准(防误报)**:候选事件必须同时满足 (a) 在 trace 里可验证为异常/低效 (b) 不属于 5 个现有 detector 的语义范围。排除"设计上就不该检测的"(如正常长思考、正常重试容错)。
3. **样本选择策略**:优先选"已知有错误的会话"(如 <session-id> 有工具报错、开发会话有 retry/RATE_LIMIT),再补普通长会话——错误多的会话盲区密度高,效率高。
4. **盲区优先级**:按"发生频率 × 可避免成本"粗估(高/中/低),高频且高成本者优先立项。

## Risks / Trade-offs

- [人工核对可能漏检] → 每个会话至少扫一遍全部 error/retry 事件(用 grep 定位 error/exit code 等关键词),不凭记忆。
- [盲区判定主观] → 用"对应最初设计类别"锚定(05 文档 L558 的五类 TOOL 缺陷 + 其他),不发明新类别。
- [样本不足] → 单样本盲区标注"待收集",不立项;样本充足(≥2)才可进 backlog。
